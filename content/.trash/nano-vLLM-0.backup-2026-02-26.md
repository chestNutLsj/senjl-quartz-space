如果把大模型推理服务想象成一条永不停歇的流水线，那么推理引擎就是那台“总控器”。但这条流水线生产的不是标准零件，而是两种截然不同的工作负载：

- prefill：一次性吞下整段 prompt，建立上下文，偏计算密集，天然拥抱大 batch。
- decode：逐 token 生成，偏访存与同步密集，天然害怕抖动与额外开销。

这对组合把“推理引擎”从一个朴素的 for 循环，瞬间变成系统设计题：吞吐和延迟如何同时被照顾？公平性如何在资源硬约束下成立？当 KV cache 成为真正的瓶颈时，谁先走、谁后走、谁被迫让路？

nano-vLLM 的价值在于它把推理引擎的骨架以最小成本暴露了出来。工业级系统复杂得多，但它们大多只是把同一副骨架“填肉”。

如果希望把这些抽象落到实现上，可以先从 [[nano-vLLM-1#从需求出发：一个推理引擎必须解决什么问题？|推理引擎必须解决的本质问题]] 和 [[nano-vLLM-1#推理引擎的通用设计模式|step 循环的通用抽象]] 两节开始对照阅读。

## 1. 问题本质：两个阶段的冲突与统一

prefill 与 decode 的冲突，本质上是“计算与存储”的拉扯。

- prefill 像在把信息写入“工作集”：用一次性的大算力，把上下文压进 KV cache，换来后续可复用的注意力记忆。
- decode 像在让工作集驱动计算：每一步都要从 KV cache 里读出越来越大的历史，再把一点点增量写回去。

因此，推理引擎里最关键的不是“有没有某个优化”，而是你如何承认并处理这对结构性矛盾。

- 如果你让 prefill 一口气吃完所有新请求，decode 的尾延迟会被拖得很难看。
- 如果你把 decode 的稳定性放在第一位，新请求的 TTFT 又会被牺牲。

nano-vLLM 选择了最容易理解的分离式推进：要么集中做 prefill，要么集中做 decode。这个选择没有“对错”，它更像是把矛盾赤裸裸地摆出来，让你看到之后所有工业级演进都在围绕什么转。

当你想进一步确认“这种矛盾如何被写进接口契约”，可以对照阅读 [[nano-vLLM-1#从 Engine 的设计反推：调度器如何设计？|从 step 契约反推调度器的约束]]。

## 2. 模块划分：控制面与数据面分离的必然性

推理引擎的复杂度，往往不是来源于某个“很难的算法”，而是来源于“必须长期演进”。只要系统要持续优化，你就需要一条经典原则：策略与机制解耦，也就是控制面与数据面分离。

你可以把引擎想成操作系统内核的一小块：

- 控制面回答“下一步算什么”：如何把请求组织成可执行批次，如何在 prefill/decode 之间取舍，如何在资源不足时做裁决。
- 数据面回答“怎么算得快”：如何把批次变成张量，如何把计算路径变得可复用，如何把 GPU 的吞吐与 CPU 的开销重新配平。

nano-vLLM 用极简的方式表达了这条分工：引擎的核心是一段永不停止的节拍循环，外部看起来像“调度 → 执行 → 回填状态”。这段循环之所以重要，是因为它定义了接口契约，一旦契约稳定，调度策略和执行优化就可以在彼此不互相污染的前提下迭代。

对应的实现入口在 [[nano-vLLM-1#nano-vLLM 的 Engine 实现细节|Engine 的节拍与模块契约]]，而“数据面如何被抽象成执行器接口”可以接着看 [[nano-vLLM-1#继续思考：如何定义执行器的设计与接口？|执行器接口与职责边界]]。

## 3. 调度器：在有限资源下做最优决策

如果说推理引擎是一台机器，那么调度器就是它的“政策制定者”。它必须在硬约束下做决策，而不是在理想世界里追求某个漂亮的最优。

调度器最典型的硬约束有两类：

- batch 约束：一次能处理多少 token、多少序列。
- KV 约束：能不能为新请求分配足够的 KV 块，能不能为运行中的请求继续追加。

这像极了操作系统的进程调度：waiting 是就绪队列，running 是执行队列；资源不足时的“抢占”不是为了优雅，而是为了让系统不崩。

但推理调度比 OS 更残酷：OS 的时间片主要在争 CPU，而推理系统的瓶颈常常在显存里的 KV。KV 一旦卡住，吞吐、尾延迟、公平性会同时变糟。于是你会看到工业界普遍走向几条路径：

- continuous batching：尽可能让 decode 的批次连续滚动，减少阶段切换带来的抖动。
- chunked prefill：把长 prompt 切块插入执行，避免 prefill 形成 head-of-line 阻塞。
- 更强的优先级与成本模型：以“系统目标”而不是“队列顺序”来裁决。

nano-vLLM 的调度策略很朴素，因此更适合作为一面镜子：它让你看到最小系统里，哪些决策已经不可避免；也让你更容易理解工业级系统为什么必须在这些点上变复杂。

如果你想从“极简策略”一路落到实现细节，可以按顺序对照 [[nano-vLLM-1#2. prefill 的 schedule|prefill 调度]]、[[nano-vLLM-1#3. decode 的 schedule|decode 调度]]，再回到 [[nano-vLLM-1#从 Engine 的设计反推：调度器如何设计？|postprocess 的状态回填与资源回收语义]]。

## 4. KV Cache 管理：虚拟内存的翻版

推理引擎最终都会被一个现实问题击中：KV cache 才是真正的“内存”。当并发上来后，你会发现调度器不是在调 token，而是在调页。

把 KV cache 看成虚拟内存，会让很多设计瞬间变得直观：

- 块（block）像页（page）：固定大小，便于分配、回收与碎片控制。
- 映射表（block table）像页表：把“逻辑位置”映射到“物理块”。
- 前缀共享像共享页：相同前缀的请求可以复用同一段历史，减少重复占用。
- copy-on-write 是工业级必修课：共享带来收益，也带来一致性与分叉成本。

nano-vLLM 的实现足够朴素，但它已经把“分页思想”引入了 KV 管理：当你能把 KV 作为一组可分配的块来思考，调度器的很多决策就不再是玄学，而是清晰的资源会计。

工业级系统会把这一层推到更远：从简单的共享走向更强的前缀缓存结构（例如基于树的索引），从“只分配不淘汰”走向 LRU/代际管理，从单机显存走向 swap/offload，甚至走向把 prefill 与 decode 的 KV 体系拆开。
如果你希望验证“分页思想如何落到接口与数据结构”，可以对照阅读 [[nano-vLLM-1#深入底层：KV Cache Block Manager 需要提供哪些服务？|Block Manager 的接口与核心方法]]。

## 5. 执行器：从灵活到极致，靠的是“预编译换运行时”

执行器的任务很简单：把一组请求变成一次 GPU 计算，再把结果带回来。但“简单”不代表“容易”。真正的挑战在于：你不能同时拥有无限灵活性和极致性能。

一种经典的分工是：

- prefill 更偏灵活：长度差异大、批次形态变化多，系统更需要快速适配。
- decode 更偏固定：每步增量很小、循环次数巨大，任何 CPU 开销都会被放大。

因此，工业界常用一条高性能系统的通用哲学来处理它：用预编译换取运行时效率。

这在推理里经常体现为图固化、算子融合、形状分桶等路径。它们都在做同一件事：承认 decode 的形状变化是有限的，然后用“提前准备好的快路径”把每一步的非 GPU 开销压到最低。

nano-vLLM 的价值在于：它用最少的机制展示了“快路径”这个思想如何嵌入一个推理引擎的骨架里。一旦你理解了这点，再去看更复杂的系统优化，会发现它们大多只是把这条路走得更彻底。

在实现层面，这些想法对应到“执行器的职责边界、输入打包与运行时组织方式”，可以从 [[nano-vLLM-1#继续思考：如何定义执行器的设计与接口？|执行器的设计与实现]] 入手。

## 6. 工业级演进：从 nano 到 vLLM/SGLang

把 nano-vLLM 当作“骨架”，工业级系统就是“骨架上长出的肌肉”。你可以用四条主线来理解这种演进，而不是陷入碎片化的优化列表。

- 调度策略：从阶段分离走向 continuous batching，从长 prompt 的阻塞走向 chunked prefill，再走向更细粒度的目标函数（吞吐、尾延迟、SLO、公平性的组合）。
- 缓存管理：从简单分页走向更强的前缀缓存结构与淘汰机制，从“单一显存池”走向 swap/offload，以及围绕共享引入更成熟的 copy-on-write 语义。
- 执行优化：从减少 kernel launch 与 CPU 开销，走向图固化/分桶/融合，再叠加量化、FlashAttention 等算子级优化，最终把瓶颈重新推回带宽与并行通信。
- 架构扩展：从单机单卡走向多卡并行（TP/PP/DP），再走向把 prefill 与 decode 解耦的服务化架构（例如 disaggregated prefill/decode），以便分别优化两种工作负载。

理解 nano 的意义在于：你拿到了一把“抽象的钥匙”。当你再去读 vLLM、SGLang，或者任何推理引擎的实现时，你会更关注它们如何处理同一组矛盾与权衡，而不是被某个具体工程细节带跑。

如果你想把这张“抽象地图”继续放大，可以从两条主线扩展阅读：vLLM 通常被概括为 paged attention（分页化 KV 管理）与 continuous batching（连续批处理）；SGLang 则更强调面向程序化推理工作流的表达与调度（尤其是复杂多轮交互与工具调用场景）。

## 结语：从代码中看到思想

读一个小而完整的系统，价值往往不在于“学会某个框架怎么写”，而在于你能从中捕捉到一组可迁移的思想。

推理引擎的本质并不神秘：它是在同一套硬件与同一份 KV 资源上，长期管理 prefill 与 decode 这对结构性冲突；它必须在硬约束下持续做决策，并把决策变成稳定可复用的执行路径。

如果你读完本文，脑海里留下的不是某段代码，而是这些矛盾与抽象，那么你就已经获得了进入工业级推理系统的正确姿势。接下来只需要沿着这些链接回到 [[nano-vLLM-1|nano-vLLM-1.md]]，把关键机制逐一对照清楚，然后再去更大的系统里验证它们如何被工程化。
